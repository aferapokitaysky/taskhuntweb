# TaskHunt — ТЗ для Gemini, раунд 8: withdrawal-калькулятор, геймификация профиля, рейтинг в откликах

Три небольших, не связанных друг с другом backend-эндпоинта — простая
логика, без хитрого скоринга (скоринг заказов/фрилансеров и тэги — это
отдельная зона оркестратора, не трогай `apps/api/src/modules/matching/`
и не переписывай `rankBidsForOrder`/`recommendOrdersForFreelancer`).

**Важно про пересечение файлов**: `orders.service.ts` и `users.service.ts`
сейчас одновременно правит оркестратор (добавляет туда `getRankedBids`,
`getRecommendedOrders` и матчинг-поля). Правь **только** конкретные
методы, указанные ниже (`getMe`, `findOne`), не трогай остальной файл,
не переформатируй импорты без необходимости — это снижает риск конфликта
при слиянии. Если после `git status` увидишь, что файл уже не совпадает
с тем, что ты видел в начале раунда — перечитай его перед правкой, не
перезаписывай вслепую.

## 1. `GET /wallet/withdrawal-fee-info`

Новый эндпоинт в `apps/api/src/modules/wallet/` (контроллер/сервис —
как тебе удобнее, но следуй существующему стилю `WalletController`).
Публичный для авторизованного пользователя (`@UseGuards(JwtAuthGuard)`,
без ролей — вывод доступен и клиенту, и фрилансеру).

Читает текущее правило комиссии за вывод (`CommissionRule` — глянь
`AdminService.updateCommissionRule`/`listCommissionRules` как образец
запроса, там уже есть работа с этой моделью; тип вывода скорее всего
называется `'WITHDRAWAL'`, проверь реальное значение `CommissionType` в
`schema.prisma`, не угадывай) и отдаёт:

```ts
{
  percentage: number, // например 1 = 1%
  fixedAmount: number, // фиксированная часть, если есть, иначе 0
}
```

Нужно фронту (оркестратор делает "прозрачный калькулятор вывода" —
живой пересчёт суммы к получению при вводе суммы вывода), поэтому
именно сырые percentage/fixedAmount, не готовую строку.

## 2. Геймификация: `profileCompleteness` в `GET /users/me`

Расширь `UsersService.getMe()` (не переписывай остальной метод) — в
ответ добавь:

```ts
{
  // ...существующие поля как есть...
  profileCompleteness: number, // 0-100, целое
  missingSteps: [{ label: string, points: number }], // только НЕ выполненные шаги, отсортированы по points убыв.
}
```

Веса (ровно так, не изобретай свои — фронт это уже расчитывает на
конкретные подсказки, веса должны совпадать с текстом на фронте):

| Условие | Баллы | label (если не выполнено) |
|---|---|---|
| `profile.avatarUrl` заполнен | 10 | "Добавьте фото профиля" |
| `profile.bio` заполнен (не пустая строка) | 15 | "Расскажите о себе" |
| хотя бы 1 навык в `profile.skills` | 15 | "Добавьте навыки" |
| `profile.githubUrl` ИЛИ `profile.websiteUrl` заполнен | 15 | "Добавьте ссылки на GitHub/Портфолио" |
| `profile.country` И `profile.city` заполнены | 15 | "Укажите местоположение" |
| `user.status === 'ACTIVE'` (email подтверждён) | 20 | "Пройдите верификацию Email" |
| есть активная подписка PRO или PREMIUM | 10 | "Оформите Pro-подписку" |

Сумма весов = 100. `profileCompleteness` — сумма баллов за выполненные
условия. Если `profile` вообще `null` (бывает до онбординга) —
`profileCompleteness: 0`, `missingSteps` — все 7 пунктов.

## 3. Рейтинг фрилансера в списке откликов заказа

Расширь `OrdersService.findOne()` (тоже не переписывай остальное) —
в каждом объекте `bids[].freelancer` добавь:

```ts
{
  // ...существующие поля freelancer как есть...
  avgRating: number | null, // среднее Review.rating, где freelancer — получатель (reviewsReceived)
  reviewsCount: number,
}
```

Простой доп. запрос `prisma.review.aggregate` / `groupBy` по
`targetId` (проверь реальное имя поля-получателя отзыва в модели
`Review` — не угадывай) для всех `freelancerId` из `bids`, не N+1 в
цикле.
