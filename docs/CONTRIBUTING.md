# Как тут работаем с git

## Ветки

- `main` — всегда стабильный, никто не коммитит в него напрямую после
  инициального Phase 1
- Каждая фича/задача — отдельная ветка: `feature/<область>-<кратко>`,
  например `feature/backend-referrals`, `feature/frontend-admin-v2`,
  `feature/notifications-service-email`
- Ветка мержится в `main` через PR (или обычный merge, если PR — оверкилл
  для конкретного изменения), после того как:
  - `pnpm --filter <app> build` проходит без ошибок
  - `prisma generate` проходит без ошибок (если менялась схема)
  - для бэкенда — хотя бы `tsc --noEmit` чистый

## Мы в одной папке, не в разных клонах

Codex и второй разработчик (или агент) физически работают в одном
рабочем каталоге на диске, а не в изолированных клонах репозитория. Из-за
этого простое "переключись на свою ветку" отдирает от рабочего дерева ещё
и чужие незакоммиченные правки. Практическое правило:

- Перед тем как начать новую фичу, закоммить (или оставь как есть, но
  зафиксируй) всё, что уже в работе — не переключай ветку с висящими
  чужими изменениями в рабочем дереве
- Если нужно работать параллельно, не мешая друг другу физически —
  используй `git worktree add ../taskhunt-<branch> <branch>`: это создаёт
  отдельную папку с тем же репозиторием на другой ветке, изменения не
  пересекаются на файловой системе, пока ветки не смёржены

## Коммиты

- Сообщения коммитов и комментарии в коде — на русском
- Один коммит — одна логическая единица работы (не "всё разом" и не
  "один файл — один коммит")
- Перед коммитом смотри `git status`/`git diff` — не подхватывай в свой
  коммит чужие незакоммиченные файлы по ошибке, если работаете в одной
  папке одновременно
